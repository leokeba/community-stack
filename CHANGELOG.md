# Changelog

All notable changes to the Community Communications Stack will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Milestone 0: Reconnaissance and Architecture Decisions:**
  - Initial threat model (`docs/threat-model.md`).
  - Architecture documentation (`docs/architecture.md`).
  - Architecture Decision Records (`docs/decisions/0001` through `0006`).
- **Milestone 1: Project Foundation:**
  - Python packaging with `pyproject.toml` and `uv` support.
  - JSON Schema specification (`config/schema.json`) for `community-stack.yaml`.
  - Operator CLI (`community-stack`) with `init`, `check`, and `plan` commands.
  - Secret management with strict `.env` loading, permission checks, and automatic redaction filter.
  - Test suite with pytest and code formatting/linting with ruff.
  - GitHub Actions CI workflow.
- **Milestone 2: Minimal Deployable Infrastructure:**
  - Modular Docker Compose services for Caddy proxy (`services/proxy`), Landing page (`services/landing`), Matrix Synapse with PostgreSQL (`services/matrix`), and Element Web client (`services/element`).
  - Network segmentation isolating database traffic (`matrix_internal`) from public ingress (`proxy_net`).
  - Ansible host preparation roles and master deployment playbook (`ansible/`).
  - Implemented `community-stack install`, `community-stack status`, and `community-stack logs` CLI commands.
  - End-to-end deployment documentation and firewall/DNS guide (`docs/deployment.md`).
  - Integration test suite for container service configurations, network policies, and healthchecks.
- **Milestone 3: Backups, Restoration, and Safe Upgrades:**
  - Implemented encrypted backup engine (`BackupEngine`) backing up PostgreSQL dumps, persistent data, config, and credentials.
  - Snapshot verification command (`community-stack backup verify`) validating manifest and archive integrity.
  - Isolated restore command (`community-stack restore --target <dir> --confirm`) with safety guards preventing unconfirmed overwrite of active environments.
  - Safe service upgrade command (`community-stack upgrade <service>`) with automatic pre-upgrade snapshots.
  - Comprehensive backup, restore, and disaster recovery runbook (`docs/backup-restore.md`).
  - End-to-end disaster recovery integration test suite (`tests/recovery/test_backup_restore.py`).
- **Milestone 4: Canonical Public Announcements:**
  - Canonical announcement domain model (`Announcement`) with strict field and length validations.
  - Durable SQLite storage engine (`AnnouncementStorage`) tracking announcements and per-adapter delivery states.
  - Web & RSS adapter (`WebFeedAdapter`) generating public HTML archive, Atom 1.0, RSS 2.0, and JSON Feed (v1.1).
  - Matrix announcement room adapter (`MatrixRoomAdapter`) posting formatted notices via Client-Server API with idempotency keys.
  - Announcement publishing orchestrator (`AnnouncementPublisher`) with failure isolation, bounded retries, and update/withdrawal propagation.
  - CLI commands: `community-stack announce create`, `list`, `show`, `update`, `withdraw`, and `retry`.
  - Comprehensive unit and integration test suite verifying multi-channel delivery and adapter failure isolation.
- **Milestone 5: Optional WhatsApp Compatibility:**
  - Integrated `mautrix-whatsapp` bridge service container (`dock.mau.dev/mautrix/whatsapp:v0.11.2`) with configuration templates.
  - Implemented `WhatsAppAnnouncementAdapter` (Mode A) for unidirectional forwarder of canonical announcements.
  - Strict room allowlisting logic in `WhatsAppBridgeManager` preventing accidental exposure of non-allowlisted private rooms.
  - Emergency disconnect killswitch command (`community-stack bridge disable --confirm`) immediately stopping bridge traffic while preserving core Matrix.
  - Comprehensive operational and privacy guide in `docs/whatsapp-integration.md`.
  - Unit and integration tests validating that WhatsApp disconnection or failure does not disrupt the core stack.
- **Milestone 6: Additional Accessible Channels:**
  - Implemented `ActivityPubAdapter` federating announcements to Mastodon/GoToSocial via ActivityStreams 2.0 `Create(Note)` and `Delete(Note)` events.
  - Implemented `EmailNewsletterAdapter` with multipart text/HTML formatting, RFC 8058 one-click unsubscribe headers, and topic filtering.
  - Built `SubscriberManager` with SQLite persistence, double opt-in validation, immediate opt-out compliance, and destination privacy masking.
  - Built ultra-lightweight, zero-JS text-mode public web portal (`services/landing/html/lite.html`) for 2G/3G connections.
  - Added CLI subscriber management: `community-stack subscribers list`, `add`, and `unsubscribe`.
  - Comprehensive evaluation of Email, SMS gateways (Kannel, Jasmin, GSM modems), and IVR voice information lines in `docs/accessible-channels.md`.
  - Integration test suite validating multi-channel broadcast and strict opt-out adherence.
- **Milestone 7: Multi-Host Resilience & Offline Continuity:**
  - Implemented `OfflineArchiveExporter` producing self-contained, offline-readable HTML & JSON archives with SHA256 integrity verification.
  - Built `community-stack archive export` and `community-stack archive verify` CLI commands for USB and local Wi-Fi distribution.
  - Added Ansible warm standby provisioning playbook (`ansible/playbooks/standby.yml`) pre-pulling container images and configuring independent hosts.
  - Comprehensive guide in `docs/multi-host-resilience.md` covering independent failure domains, captive portal Wi-Fi setup (OpenWrt/Raspberry Pi), and Meshtastic/LoRa off-grid mesh evaluation.
  - Unit and integration tests verifying offline archive generation and cryptographic tampering detection.
- **Milestone 8: Production Hardening, Operator Handbook & Governance:**
  - Enhanced `community-stack doctor` with live storage capacity checks and container network port isolation audits.
  - Authoritative Operator Handbook in `docs/operations.md` covering daily maintenance, upgrading pinned releases, incident response runbooks, and decommissioning.
  - Maintainer handover and governance guide in `docs/governance.md` covering the two-person rule, access escrow, credential rotation, and upstream license compliance.
  - Unit and regression test suite verifying diagnostic audits and security redactions.
- **Roadmap Phase 0: Durable delivery jobs:**
  - Every channel delivery is recorded as a job in the announcements database before it runs, so a crash mid-dispatch no longer loses deliveries.
  - Temporary, safely repeatable failures are retried automatically with exponential backoff (30 s to 1 h, 5 attempts).
  - Background delivery loop inside the admin app, plus `community-stack announce worker` for running it standalone.
  - Withdrawals and disabled channels cancel pending retries; a newer update supersedes a pending publish.
  - Admin dashboard and announcement pages show deliveries waiting for an automatic retry.
- **Roadmap Phase 0: Connector capability model:**
  - Channel adapters declare a readable label, a text limit, media support, and whether edits and withdrawals change the original post or send a follow-up message.
  - Each announcement page lists the channels it goes to, flags text that is too long for a channel, and says what an edit or withdrawal will do on each one.
- **Roadmap Phase 0: Accounts, roles and activity log:**
  - Several admin accounts with Owner, Admin, Publisher and Reviewer roles; every admin page and action checks the role on the server.
  - The existing single administrator becomes an Owner automatically; at least one active owner always remains.
  - Accounts page to add accounts, change roles, disable or re-enable access, and reset passwords; My account page to change your own password.
  - Role changes, disabling and password resets apply to existing sessions immediately.
  - Activity log of sign-ins, failed sign-ins, account changes, publishing actions and settings changes, kept for about 13 months.
- **Roadmap Phase 0: Encrypted backups with restic:**
  - New `operations.backups.encryption` setting (`restic` or `none`); `community-stack init` and the example configuration default to `restic`.
  - With restic, snapshots are encrypted on the host into a local, S3 or SFTP repository, verified with `restic check` plus a content listing, restored without leaving a scratch copy, and pruned by retention days. No plaintext archive is kept.
  - Restic receives only backup settings, never the other secrets in `.env`.
  - `community-stack check`, `plan` and `backup` say when backups are unencrypted or restic is missing; configurations without the setting keep the previous owner-only archives.
  - The Ansible host role installs restic, and CI runs the encrypted backup tests against a real restic binary.
- **Roadmap Phase 0: Control agent skeleton:**
  - Design record [ADR 0007](docs/decisions/0007-control-agent.md): a privileged host service performs console actions from a fixed catalog over a local Unix socket.
  - `community-stack agent serve` with a hardened systemd unit (`services/agent/community-stack-agent.service`); the socket is limited to the console's group and, on Linux, to allowed peer UIDs.
  - First operations: service status, create backup, verify backup, and a restore drill that restores into a scratch folder, checks it, and deletes it.
  - The agent checks each request's parameters, the account's role (read-only from the admin database), and for the restore drill the person's password, with five attempts per 15 minutes; it runs one change at a time and writes its own audit log.
  - Admin console System page for owners and admins, which explains when the agent is not installed.
  - `deploy-vps.sh` restarts the agent after deploying, when it is installed.
- **Roadmap Phase 1: Scheduled publishing:**
  - Drafts can be scheduled from the announcement page or with `community-stack announce schedule`, in the community time zone set by the new `project.timezone` setting.
  - The background worker publishes scheduled announcements when due; claiming a publication is atomic, so concurrent workers never publish twice.
  - Scheduled announcements can be edited, published early, cancelled back to a draft, or withdrawn.
- **Roadmap Phase 1: Wave-1 connectors:**
  - Mastodon, Bluesky, Telegram channel, Discord and Slack connectors, connected from a new console Channels page with step-by-step instructions, a connection test, and write-only credentials.
  - Long announcements are shortened to each channel's limit with a link to the full announcement; edits and withdrawals use the post ID each channel returned, and channels that cannot edit or delete are skipped instead of reporting a false success.
  - Bluesky posts use a stable record key, and Mastodon posts an idempotency key, so retries cannot post twice; Discord posts never ping, and Slack text is escaped.
  - Connector URLs must be HTTPS and resolve to public addresses, at connection time and before every request.
- **Roadmap Phase 1: Service settings and setup checklist:**
  - Console Services page to change the community time zone, backup retention and encryption, and to turn Element and Matrix on or off, through new agent operations `config.get`, `config.plan` and `config.apply`.
  - Every change is reviewed with the exact configuration diff, then backed up, written in place (keeping comments and the file mounted into containers), applied, health-checked, and rolled back automatically if a service does not come back healthy.
  - Stopping Matrix requires the person's password, checked by the agent; enabling restic encryption requires restic and `RESTIC_PASSWORD` on the server.
  - Get started checklist (accounts, agent, time zone, encrypted backups, restore drill, channel, first announcement), linked from the dashboard until complete.
  - The community time zone is read on each use, so changes apply without restarting the console.
- **Roadmap Phase 1: Editor with formatting and channel previews:**
  - Announcement messages are Markdown (headings, emphasis, lists, links), rendered with raw HTML disabled; line breaks keep working as before.
  - The web feed, Atom and JSON feeds, email, Matrix and ActivityPub get formatted HTML; other channels get plain text without Markdown symbols.
  - Live preview in the editor of the formatted announcement and of the exact text each channel will receive, with character counts and shortening notices.
  - Optional custom text per channel for Mastodon, Bluesky, Telegram, Discord and Slack.
- **Roadmap Phase 1: Images with descriptions:**
  - One image per draft or scheduled announcement, uploaded on its page with a required description; JPEG, PNG, WebP or GIF up to 10 MB.
  - Uploads are checked with Pillow, rotated upright, stripped of EXIF and other metadata (including GPS location), resized to 1600 px, and protected against decompression bombs.
  - Images are private until publication, copied to the public feed with Open Graph tags when published, and removed when withdrawn.
  - Mastodon and Bluesky upload the image natively with its description (Bluesky re-encoded under 1 MB); Discord attaches it with its description; Slack, ActivityPub and email reference the public image with its description. Matrix and Telegram do not send images yet.
- **Roadmap Phase 1: Health and logs:**
  - Agent operations `health.get` (disk space, latest backup age, certificate expiry for the web and Matrix domains, container state and health) and `logs.get` (last 50, 200 or 500 lines of one service).
  - Logs are redacted in the agent: `.env` values, saved channel credentials, bearer tokens and Telegram bot tokens.
  - Console Health page for owners and admins.
- **Roadmap Phase 1: Email newsletter through listmonk:**
  - listmonk connector on the Channels page (address, API user and token, list IDs) with a connection test that checks the lists exist.
  - Each announcement becomes one Markdown campaign, with its image and a link to the online version, started immediately; the announcement ID in the campaign name makes retries reuse it instead of sending twice.
  - Edits send one "Update" email per revision and withdrawals one correction email.
- **Roadmap Phase 1: Automatic and off-site backups:**
  - The control agent runs scheduled backups (hourly, daily or weekly, now changeable on the Services page) and verifies each one; failures retry after an hour and show on the Health page.
  - Console Backups page: where backups go, the last automatic run, a guided switch to any S3-compatible bucket (tested with a first verified backup before it takes effect, rolled back on failure), switching back to local disk, and the offline archive download.
  - The agent's audit log redacts secret parameters such as access keys.
  - The offline archive now contains only published announcements; it previously included drafts and scheduled announcements.
- **Roadmap Phase 1: Two-step login and account recovery:**
  - Optional TOTP two-step login with QR-code setup (password required to start), ten single-use hashed recovery codes, replay protection, and a code step limited to five attempts in five minutes.
  - Owners and admins can turn off two-step login for an account that lost its phone; the Get started checklist asks every owner and admin to turn it on.
  - `community-stack admin list | reset-password | reset-two-step` recovers accounts from the server when nobody can log in; it refuses to run as root against a user-owned database.
- **Roadmap Phase 1: Fresh-server bootstrap:**
  - `scripts/bootstrap.sh` takes a fresh Debian or Ubuntu server to the browser setup page: packages, Docker, a service account, the code, configuration and secrets, a firewall that keeps SSH open, the services, and the control agent; `--dry-run` shows every step and re-runs keep existing data.
  - `community-stack init` gains `--project-name`, domain, `--timezone`, `--acme-email`, `--console-uid/--console-gid` and `--setup-token` options, and creates the announcements and feed data directories.
  - `install`, `upgrade` and the agent generate Synapse's configuration (PostgreSQL, signing key, ownership) and Element's configuration on first start, never overwriting existing files; the generated Synapse configuration is checked by an opt-in test that boots real Synapse and PostgreSQL containers.
  - Element now reads `data/element/config.json` generated for this homeserver; it previously pointed at `http://localhost`. Caddy receives the domains and ACME email from `.env`.
  - Deploys fall back to pip on servers without uv.
- **Roadmap Phase 2: Review before publishing:**
  - Optional review mode (Settings): drafts are submitted, approved or sent back with a note by someone other than the submitter, and only approved announcements can be published or scheduled.
  - Editing a submitted, approved or scheduled announcement returns it to draft; images can only change on drafts while review is on.
  - Reviewers can now approve; the dashboard lists announcements waiting for your review, and each announcement shows its review history.
  - Urgent publication without review for owners and admins, with a required reason and password, recorded in the review history and activity log.
- **Roadmap Phase 2: Templates:**
  - Templates page to create, edit and delete reusable announcements (title, message, author, tags, per-channel text), validated like announcements.
  - Start a draft from a template, or save any announcement as a template.
- **Roadmap Phase 2: Service updates from the console:**
  - Agent operations `services.versions` and `services.update`: compare running images with the release's pinned images, then back up, pull, restart and health-check one service, restarting the previous images if the new ones are not healthy.
  - Services page lists versions with upstream release notes and an Update button; PostgreSQL major-version changes are refused.
- **Roadmap Phase 2: The community's own fediverse account:**
  - A followable ActivityPub account on the website domain (WebFinger, actor, outbox, followers, notes), connected from the Channels page.
  - Inbox accepts Follow and Undo only with a verified HTTP signature whose key belongs to the activity's actor; replies with a signed Accept.
  - Announcements are delivered as signed Create, Update and Delete activities, once per follower server (shared inboxes), with formatting, image and alt text; failures are retried safely.
  - Caddy routes for `/ap/` and `/.well-known/webfinger`, added to existing Caddyfiles by `deploy-vps.sh`; new dependency: cryptography.
- **Roadmap Phase 2: SMS alerts and public sign-up:**
  - SMS connector for SMS Gateway for Android (cloud or private server): batched sends with stable IDs so retries never text twice, a stop link in every alert, corrections on withdrawal, and no texts for edits.
  - Public `/subscribe` and `/subscribe/stop` pages with explicit consent, texted 6-digit confirmation codes (15 minutes, five tries, three per number and ten per visitor per day), a honeypot field and CSRF protection.
  - Caddy route for `/subscribe`, added to existing Caddyfiles by `deploy-vps.sh`.
- **Roadmap Phase 2: Signal (experimental):**
  - Optional `signal` service (signal-cli-rest-api 0.101), switchable on the Services page, reachable only on an internal network shared with the announcements service.
  - Linking page that shows the QR code to scan from Signal's Linked devices and lists the account's groups to choose from.
  - Signal connector that posts to the chosen group, edits with `edit_timestamp` and withdraws with remote delete; only rate-limited posts are retried automatically.
- **Roadmap Phase 2: Mirroring Matrix rooms:**
  - Mirroring page to follow chosen Matrix rooms with the announcements account: whose messages count (moderators or everyone), publish directly or create drafts for review, and which channels receive them.
  - New messages become announcements, Matrix edits update them and deletions withdraw them; history is never imported, the account's own posts are ignored, and each room is limited to ten announcements an hour.
  - Announcements can now target a subset of channels, and edits and withdrawals only go to channels that received the announcement.
- **Synapse 1.163.2:**
  - Pinned Synapse moves from 1.119.0 to 1.163.2 (security fixes, including the Pillow fix in 1.163.2). Upgrades from 1.119 were tested on SQLite, as production uses, and on the stack's generated PostgreSQL configuration: Synapse migrated and existing users could log in. Fresh installs boot healthy on the new version.
  - After deploying, update Matrix from the console's Services page; it takes a safety backup first. If a Synapse update fails after migrating its database, the console names the backup to restore.
